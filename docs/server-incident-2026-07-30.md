# 本地开发机卡死事件取证

取证时间：2026-07-30（Asia/Singapore）

## 结论

发生卡死的是本地开发机 `research-mjx`。系统在 14:10 重新启动，上一轮启动于 14:09 附近中断，日志中没有正常关机序列。

根因是本地长期累积的多批 `nms-naturalness` Docker 版本容器同时运行并发生内存回收风暴。大量容器没有内存上限，部分使用 `restart: unless-stopped`，重启后又自动拉起。

## 关键证据

- 内存使用率从约 `84.7%` 升至 `95.6%`，可用内存降至约 `0.8 GB`。
- 进程/线程数从约 `3808` 升至 `4791`。
- 系统负载从约 `0.53` 升至 `290`，阻塞任务峰值约 `225`。
- I/O wait 达到约 `86%–87%`。
- page-in 达到约 `256 MB/s`，major fault 约 `2300/s`，伴随高强度页面扫描。
- 主机有 8 GB swap，但 `vm.swappiness=0`，事件期间 swap 使用量保持 0。
- 重启后 v24–v38 等旧版本容器自动恢复，`system.slice` 内存峰值达到约 `63.6 GB`，与内存争抢根因一致。
- 没有磁盘硬件错误；高磁盘队列来自页面回收和缺页读入。

`snapd` watchdog、容器健康检查超时、网络缓冲和 TLS 超时均属于资源耗尽后的连锁症状。

## 事件后状态

旧版本容器在 14:19 左右被另一管理流程停止。取证完成时仅 v47 运行，约使用 1.8 GB；主机约 12 GB 已用、48 GB 可用。

本次取证保持只读，没有停止或重启不属于赔了么的容器。

## 建议

1. 每个版本服务配置明确的内存和 CPU 上限。
2. 只允许当前版本使用自动重启策略，历史版本部署后及时下线。
3. 给版本容器增加统一标签和过期清理策略。
4. 调整 swap/zram 策略，为突发内存压力保留缓冲。
5. 对内存可用量、blocked tasks、major faults、I/O wait 和容器数量设置告警。
